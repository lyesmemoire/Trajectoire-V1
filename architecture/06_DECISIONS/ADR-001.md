# ADR-001: Restructuration DDD

## Contexte

L'architecture actuelle du projet Trajectoire est partiellement structurée selon les principes DDD (Domain-Driven Design). Les domaines métier sont identifiés mais leur structure interne ne suit pas les couches DDD classiques (Domain, Application, Infrastructure, Presentation).

### État Actuel
- **Bounded Contexts identifiés**: Identity, Interview, Career, ATS, Voice, Analytics, AI, Security, Orchestration
- **Structure actuelle**: Fichiers mélangés dans des dossiers lib/* sans séparation claire des responsabilités
- **Dépendances**: Couplage variable entre domaines (0-5 dépendances)
- **Tests**: Aucun test dans les domaines métier (0% de couverture)

### Problèmes
1. **Absence de séparation des responsabilités**: Logique métier, infrastructure et application sont mélangées
2. **Couplage élevé**: Certains domaines dépendent de plusieurs autres domaines
3. **Absence de tests**: Aucun test dans les domaines métier
4. **Maintenance difficile**: Structure non standardisée

---

## Décision

Restructurer tous les bounded contexts en DDD complet avec les couches suivantes:
- **Domain Layer**: Entities, Value Objects, Domain Services
- **Application Layer**: Use Cases, Application Services
- **Infrastructure Layer**: Repositories, External Services
- **Presentation Layer**: Controllers, DTOs (pour les applications)
- **Tests Layer**: Unit Tests, Integration Tests

### Structure Cible
```
lib/{context}/
├── domain/
│   ├── entities/
│   ├── value-objects/
│   └── services/
├── application/
│   ├── use-cases/
│   └── services/
├── infrastructure/
│   ├── repositories/
│   └── services/
└── tests/
    ├── unit/
    └── integration/
```

---

## Conséquences

### Positives
- **Séparation claire des responsabilités**: Chaque couche a un rôle bien défini
- **Tests plus faciles**: Isolation des use cases et repositories
- **Couplage réduit**: Dépendances unidirectionnelles (Application → Domain → Infrastructure)
- **Maintenance améliorée**: Structure standardisée et documentée
- **Évolutivité**: Ajout de nouvelles fonctionnalités plus facile

### Négatives
- **Effort de migration**: Restructuration de tous les domaines (15 semaines estimées)
- **Courbe d'apprentissage**: Équipe à former sur DDD
- **Complexité initiale**: Plus de fichiers et de dossiers

---

## Alternatives

### Alternative 1: Garder l'architecture actuelle
**Avantages**:
- Aucun effort de migration
- Équipe familière avec la structure actuelle

**Désavantages**:
- Problèmes de maintenance persistants
- Couplage élevé persistant
- Absence de tests persistante

**Rejet**: Les problèmes actuels sont critiques et nécessitent une restructuration.

---

### Alternative 2: Refactoring complet
**Avantages**:
- Architecture propre dès le départ
- Possibilité de repenser tous les choix techniques

**Désavantages**:
- Effort beaucoup plus important
- Risque de régression élevé
- Temps de développement plus long

**Rejet**: Trop risqué et coûteux. Migration incrémentale plus sûre.

---

### Alternative 3: Restructuration partielle
**Avantages**:
- Effort réduit
- Migration plus rapide

**Désavantages**:
- Incohérence dans l'architecture
- Problèmes non résolus dans les domaines non migrés

**Rejet**: Incohérence architecturale à éviter.

---

## Implémentation

### Phase 1: Préparation (1 semaine)
- Créer les ADRs
- Préparer les outils de migration
- Documenter l'état actuel

### Phase 2: Migration Platform Context (1 semaine)
- Isoler l'infrastructure dans platform/
- Déplacer les modules d'infrastructure
- Mettre à jour les imports

### Phase 3-11: Migration des Bounded Contexts (9 semaines)
- Restructurer chaque bounded context en DDD
- Ajouter des tests (90% de couverture)
- Documenter les contracts

### Phase 12: Nettoyage (1 semaine)
- Supprimer les modules morts
- Supprimer les dossiers vides
- Nettoyer la documentation obsolète

### Phase 13: Validation Finale (1 semaine)
- Valider que l'application fonctionne
- Valider que les tests passent
- Valider que la documentation est à jour
